# Quest port Auto-Cloud bridge

Monster Train 2 (2742830) is registered alongside StS2. Shared UID and matching signing are required.
`PortAutoCloud.java` is shared with the port APK. Rebuild ports with the updated shared source to use the lifecycle lock. The port invokes it before Unity starts. The service invokes it after registered process death, before releasing the Steam app session.

Steam itself downloads/uploads Auto-Cloud through its existing logged-in session. The bridge maps root 12 (WinAppDataLocalLow) to the Quest external files directory, using the Proton-prefix save tree Steam actually downloads. Every cloud file used for reconciliation must match its SHA1 in `remotecache.vdf`. The inventory and file contents are rechecked before mutation. The bridge never reads login files or handles credentials. `tools/cloud_inventory.c` remains a read-only RemoteStorage diagnostic. Its enumeration provides no authority to delete Auto-Cloud files.

Default mode is download-only, with reports under runtime `files/autocloud/2742830-before-start.json` and `2742830-after-exit.json`. Losing bytes are retained on Quest as `.conflict-<epoch-seconds>-<hash-prefix>` before replacement. `preferences-local.json` is local-only according to the actual Steam rules.

After reviewing the first report, create runtime `files/autocloud/2742830.allow-uploads` to permit staging at process exit. The marker is checked again at the mutation boundary. Startup reconciliation always uses download-only mode. The Steam client performs network synchronization on app-session exit. Confirm completion using `cloud_log.txt` and refreshed cache hashes.

MT2's saved local examples and `SaveDataJson`/`EditorManagedSaveData` serialization use JSON objects. This includes metagame backups, preferences, active saves, and run history. Reconciliation rejects empty files, malformed UTF-8, truncated JSON, trailing data, and lenient JSON syntax. It compares bytes, size, and mtime across a 250 ms stability check and checks the snapshot again before mutation. Uploads use the validated snapshot bytes.

Runtime `files/autocloud/2742830-state.json` stores per-file local and cloud hashes, the inventory ChangeNumber and timestamp for diagnostics, and the account owning that history. Writes use temporary files, fsync, and replacement. Existing local files are recorded before reconciliation, including files whose JSON validation fails. Validated unreconciled local files also record `seen_local_sha`. After local deletion, only a different per-file cloud SHA1 permits a download, subject to a valid, non-future cloud timestamp. Inventory-wide ChangeNumber changes have no effect on this decision. Without `cloud_sha`, compare against `seen_local_sha` (or a legacy `local_sha`). Hashless legacy records retain deletion protection because their last local content cannot be reconstructed. An absent file with no history can receive a new cloud download. A change of cloud account blocks reconciliation pending explicit history review.

When both sides have a common baseline, hashes determine which side changed. Concurrent changes retain both copies and block replacement. A one-sided change follows the content baseline even when mtimes disagree. Without a baseline, time-based selection requires a gap greater than 120 seconds between valid, non-future timestamps. Divergent saves with any future timestamp are retained for review. Near-equal timestamps and invalid/future timestamps produce a conflict report and preserve the cloud copy alongside the local save.

After staging an upload, both `local_sha` and the expected `cloud_sha` record the uploaded content hash. The next pass verifies the mirror against `remotecache.vdf` before any decision. An inventory still describing the pre-upload bytes blocks that file until Steam acknowledges the upload. Once acknowledged, another local change can upload again. A different validated cloud hash is treated as a real cloud change and concurrent local changes produce a content conflict.

Cloud deletion is allowed only for exactly `saves/save-singlePlayer.json`, only at opted-in process exit, with the local file absent, and only while the cloud hash equals the recorded reconciled per-file hash. The local `run-history/RunHistory.json` must contain a matching `runId`, a full entry and embedded full `runDataJson` with the same `id`, and an explicit false `endless` flag. MT2 submits full single-player records on end/abandon. An updated meta save alone supplies insufficient completion evidence. The history snapshot, absent local path, upload marker, cloud bytes, and inventory are rechecked before deletion. The old cloud bytes are preserved as a conflict copy. Before removing the mirror file, the bridge durably records a deletion tombstone with `reconciled: true`, absent `local_sha` and `cloud_sha` keys, and `deleted_cloud_sha` containing the deleted content hash (legacy explicit JSON nulls remain readable). This makes absent cloud content the expected baseline. A recreated local run waits while Steam still lists a live entry whose mirror bytes are missing. Once Steam removes or tombstones that entry, it can upload at opted-in process exit; lingering tombstone mirror bytes block replacement until Steam removes them. Disabled uploads and startup retain the new run locally. A different validated PC hash remains a cloud change and conflicts with a new Quest run, or downloads when the local run is absent. If interrupted after recording intent, the exact deleted bytes can be safely retried using the same completion and mutation guards. Other paths, including development/staging copies, retain cloud preservation through delete-and-rename crashes.

Before-start reconciliation and the complete after-exit reconciliation/session-release pass share `files/autocloud/2742830.lock`, using a JVM monitor and an OS file lock across the runtime and port APKs. The service checks `port-processes` registrations using the registered PID and Linux start time, direct `/proc/<pid>` existence, and ActivityManager observations for the shared UID. ActivityManager package/process names also cover startup before registration. A changed start time identifies PID reuse. The service never enumerates `/proc`. Positive liveness suppresses the pass, and a second check suppresses release if a relaunch appeared during reconciliation. Missing PID evidence or an unreadable registration directory gets a 15-second grace period measured with `SystemClock.elapsedRealtime()`. The service logs entry into uncertainty and logs once when the timeout treats that identity as not alive. Positive evidence resets its timer. Registration and AppID identities have independent timers.

QA round 2 finding 2 correctly identified that `if (processes == null) return true` could block after-exit work forever. Its blanket assertion that Android 12L necessarily returns null for this app is rejected. AOSP Android 12 permits `domain proc:dir r_dir_perms`, while init mounts procfs with `hidepid=2,gid=readproc`. Hiding other UIDs does not by itself deny listing the directory. This runtime and the signed port share `com.steamruntime.shared`, so same-UID visibility is relevant. Quest-specific policy and the actual result remain unverified because this round uses no device access. Both null and filtered listings are bypassed by the new registered-PID path. [AOSP directory policy](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/android12-release/public/domain.te), [AOSP procfs mount](https://android.googlesource.com/platform/system/core/+/refs/tags/android-12.0.0_r31/init/first_stage_init.cpp).

Logged-off state blocks changes. Missing, ambiguous, changing, or empty cloud inventories block reconciliation. A live inventory entry (`persiststate != 2`) whose mirror bytes are absent always blocks that file with `cloud not materialized`, whether or not local bytes exist. Before-start reports `start_allowed: false` and `ok: false` for an unmaterialized metagame save so launchers can delay or abort. The current game activity calls the bridge but ignores its return value; upload remains blocked even if the game starts and creates an empty save. Tombstone (`persiststate = 2`) bytes are never loaded as a live save. Missing local tombstones are skipped; existing local tombstones are considered only for the single-player run or reconciled history. Unexplained cloud deletion with unchanged local content reports a content conflict and retains local bytes. Present live mirror bytes must match the inventory hash, and a newly appearing mirror file blocks upload. A bad file is reported without aborting unrelated files. Numeric `syncstate` values alone never authorize deletion. Empty RemoteStorage enumeration supplies no evidence that an Auto-Cloud account is empty.
