# Quest port Auto-Cloud bridge

Monster Train 2 (2742830) is registered alongside StS2. Shared UID and matching signing are required.
`PortAutoCloud.java` is shared with the port APK. Rebuild ports with the updated shared source to use the lifecycle lock. The port invokes it before Unity starts. The service invokes it after registered process death, before releasing the Steam app session.

Steam itself downloads/uploads Auto-Cloud through its existing logged-in session. The bridge maps root 12 (WinAppDataLocalLow) to the Quest external files directory, using the Proton-prefix save tree Steam actually downloads. Every cloud file used for reconciliation must match its SHA1 in `remotecache.vdf`. The inventory and file contents are rechecked before mutation. The bridge never reads login files or handles credentials. `tools/cloud_inventory.c` remains a read-only RemoteStorage diagnostic. Its enumeration provides no authority to delete Auto-Cloud files.

Default mode is download-only, with reports under runtime `files/autocloud/2742830-before-start.json` and `2742830-after-exit.json`. Losing bytes are retained on Quest as `.conflict-<epoch-seconds>-<hash-prefix>` before replacement or deletion staging. `preferences-local.json` is local-only according to the actual Steam rules.

After reviewing the first report, create runtime `files/autocloud/2742830.allow-uploads` to permit staging at process exit. The marker is checked again at the mutation boundary. Startup reconciliation always uses download-only mode. The Steam client performs network synchronization on app-session exit. Confirm completion using `cloud_log.txt` and refreshed cache hashes.

MT2's saved local examples and `SaveDataJson`/`EditorManagedSaveData` serialization use JSON objects. This includes metagame backups, preferences, active saves, and run history. Reconciliation rejects empty files, malformed UTF-8, truncated JSON, trailing data, and lenient JSON syntax. It compares bytes, size, and mtime across a 250 ms stability check and checks the snapshot again before mutation. Uploads use the validated snapshot bytes.

Runtime `files/autocloud/2742830-state.json` stores per-file local and cloud hashes, the cloud ChangeNumber and timestamp, and the account owning that history. Writes use temporary files, fsync, and replacement. Existing local files are recorded before reconciliation, including files whose JSON validation fails. An absent file with history remains a local deletion across restarts. An absent file with no history can receive a new cloud download. A change of cloud account blocks reconciliation pending explicit history review.

When both sides have a common baseline, hashes determine which side changed. Concurrent changes retain both copies and block replacement. A one-sided change follows the content baseline even when mtimes disagree. Without a baseline, time-based selection requires a gap greater than 120 seconds and no greater than 24 hours. Divergent saves with any future timestamp are retained for review. Near-equal timestamps and excessive skew produce a conflict report and preserve the cloud copy alongside the local save.

With the upload marker present at exit, a local deletion can be staged by removing the mirrored cloud file. This requires its hash, ChangeNumber, and timestamp to match the last reconciled revision, a nonfuture cloud timestamp, and a retained conflict copy. A local deletion whose cloud revision changed stays pending and leaves cloud bytes intact. The durable history continues to prevent resurrection. Steam's Auto-Cloud handles on-disk writes and deletions at session exit. Network deletion remains unverified until Steam refreshes its inventory. [Steam Cloud documentation](https://partner.steamgames.com/doc/features/cloud), [RemoteStorage batch documentation](https://partner.steamgames.com/doc/api/ISteamRemoteStorage#BeginFileWriteBatch).

Before-start reconciliation and the complete after-exit reconciliation/session-release pass share `files/autocloud/2742830.lock`, using a JVM monitor and an OS file lock across the runtime and port APKs. The service checks for live registrations of the same AppID and scans package processes, including pre-SteamAPI startup processes. A live port suppresses the after-exit pass. A second live-process check suppresses session release if a relaunch appeared during reconciliation.

Logged-off state blocks changes. Missing, ambiguous, changing, or empty cloud inventories block reconciliation. Deleted or absent mirror entries are skipped individually, including deletion tombstones, and a bad file is reported without aborting unrelated files. Numeric `syncstate` values alone never authorize deletion. Empty RemoteStorage enumeration supplies no evidence that an Auto-Cloud account is empty.

## Offline verification

Run `powershell -NoProfile -ExecutionPolicy Bypass -File tools/test-autocloud.ps1`. The runner compiles the production bridge using JDK 17, host-only Android stubs, and an existing cached `org.json` JAR. Override `-JavaHome` or `-JsonJar` for another offline installation. Tests use temporary directories and synthetic save objects. Coverage includes malformed and changing saves, durable deletion history, revision-checked deletion staging, new downloads, clock conflicts, cloud tombstones, upload opt-in, relaunch suppression, and thread/process locking.

Build the runtime using `powershell -NoProfile -ExecutionPolicy Bypass -File build-quest.ps1`. It creates the standalone debug APK and copies it to the script's configured local output. The 2026-11-13 verification passed 43 host-side tests with zero failures and built the runtime APK using this script. Quest/device verification remains pending.
